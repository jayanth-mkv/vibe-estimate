## Deploy what already works

**Largely delivered.** This work was carried out on `fix/initial-production` and consolidated into this branch. Read [production-readiness.md](../production-readiness.md) for the decisions and [infrastructure-inventory.md](../infrastructure-inventory.md) for the actual resource record. This section now describes what shipped and what is still open, rather than what to build.

Terraform manages it through a **new isolated root, `infra/production/`** — not the older flags in `infra/variables.tf` and `infra/cloud-run.tf`, which remain unused. The existing `infra/gemini-local` resources and the Firebase database and providers stay under their current management.

**Shipped:** Cloud Run, Cloud Tasks and Cloud Scheduler APIs enabled; a scale-to-zero Cloud Run application with a public invocation binding; a bounded review queue and an authenticated once-per-minute recovery scheduler; three dedicated service accounts, two narrow custom roles and six project IAM memberships; a private image repository and build-source bucket; the browser SDK configuration in Secret Manager with a write-only version and an accessor binding; and Firebase authorized domains imported through a GET and PATCH restricted to that single field, preserving existing domains and providers. 27 resources in that root. Cloud Build published an immutable image digest for an audited 83-file archive, and the public `/health` returned HTTP 200 with production Firebase, cloud Firestore and live Vertex.

Two architectural decisions differ from the original sketch and are the better ones:

- **A same-origin Next.js gateway** (`frontend/src/app/api/[...path]/route.ts`) forwards only authorization and content-type headers to the backend, instead of a separately hosted frontend with a pinned cross-origin `FRONTEND_ORIGIN`. It bounds bodies at 48 KiB, never follows upstream redirects, does not cache private responses, sanitizes transport failures, and does not auto-retry mutations. This resolved a real preflight mismatch where `localhost:3000` was accepted and `127.0.0.1:3000` rejected.
- **The observer runs inside managed Cloud Tasks requests** (`backend/src/room-tasks.ts`) rather than the 500 ms in-process poller, which was issuing 172,800 Firestore queries a day even with no queued rooms. [v2](v2.md) inherits this: the crew's long jobs extend the existing Cloud Tasks path rather than introducing a parallel Pub/Sub mechanism, unless a pull-based worker pool is separately justified.

**Still open in v1:**

- Full public user journeys against the deployed URL — sign-in, room, multi-turn review, draft, share, export — with evidence recorded separately from every local run. This is the release gate.
- The `dev-tutorial=cloud-run-ai-challenge` label on every Cloud Run resource.
- A deployment README with reproducible steps, and the published `firestore.rules`, which denies all direct client access so the API remains the only data path.
- Verify `readConfig` in `backend/src/config.ts` **fails closed** against a deliberately misconfigured deploy rather than trusting that it does.
- **Repository security instructions and build history — present.** The operator confirmed this agent-assisted repository as the build workflow. Preserve its instructions, commits and executed results; no separate AI Studio UI session is claimed. See [build provenance and evidence](../ai-studio-evidence.md).

**One honest caveat to carry forward.** The Secret Manager entry holds the browser SDK configuration; the runtime reaches Vertex through a keyless attached service identity billed to the cloud project. That follows Google's production authentication guidance, but it is **not** the codelab's Gemini API-key-in-Secret-Manager integration, and must not be described as such. The separate Developer API credential still returns HTTP 429 with a prepaid-balance category.

## Model fallback

The codelab describes recoverable-error model fallback, and Stability is a judging pillar. The application currently selects one explicit verified model and returns a visible retryable failure with no fixture fallback — which is correct behaviour, but not a fallback policy.

v1 adds a **bounded, tested multi-model ladder**: an ordered list of verified models, a fixed maximum number of attempts, and advancement only on a recoverable upstream error — never on a validation failure, and never into fixture output. The model that actually answered is recorded on the analysis and surfaced in the health endpoint. Attempt budgets are spent per attempt, using the existing reservation in `RoomStore.claim`, so a ladder cannot multiply spend silently.

**Gate:** each rung exercised, exhaustion producing a visible retryable failure, a validation error proven not to advance the ladder, and no path from a live failure to fixture output. Until those tests exist, do not claim fallback was tested — see [ai-studio-evidence.md](../ai-studio-evidence.md).

## Scene foundation

A new workspace package `packages/scene-schema` holds versioned graph types and zod schemas. A sibling `packages/context-kit` is created here as a stub and grows in v2.

**Units.** Integer millimetres are canonical in the stored document; metres appear only at the renderer boundary; rotations are explicitly bounded. The original drawing's coordinates are retained alongside, so a later comparison against the source is possible.

**Measurement states.** Every dimension carries one of `plan-labelled`, `user-confirmed`, `calibrated`, `assumed`, `unknown`. Unknown scale and assumed dimensions can never produce a confirmed measurement for an estimate. A default ceiling height or wall thickness is always disclosed and editable.

**Validation** is pure and fully unit-testable, with no I/O: finite coordinates, simple closed room boundaries, shared-wall topology, wall joins, positive dimensions, and openings contained within their walls.

**Revisions.** `SceneRevision` is immutable and carries `parentRevisionId`. Every write includes `baseRevisionId` and a request ID. If the head has moved, the write returns a readable conflict and **both options are preserved** — never a silent last-writer-wins. Undo creates a new revision rather than rewriting published history.

**Storage.** Scene chunks are at most 128 KiB per Firestore document, with no binary meshes. The blob-before-manifest commit ordering is established here even though v1 has no large blobs yet: write and validate immutable content first, then transact the scene head. A failed head update leaves unreferenced content for safe cleanup, never a partially published scene.

**Levels.** The schema carries a `levels[]` array from day one with exactly one level populated, so [v3](v3.md#multiple-floors)'s multi-storey work is additive rather than a rewrite.

## The sample home and the studio

A complete authored apartment — living/dining, kitchen, two bedrooms, two bathrooms, balcony — labelled plainly as a sample. Hand-authored, deterministic, no model involved.

**Views.** **Overview** is an orthographic cutaway; cutaway hides surfaces for viewing without deleting them. **Inside** enters at a chosen room with a visible exit and reset control. **Plan** supplies precision editing and, from v2, the source overlay.

Camera position, cutaway and daylight mood are **viewing preferences**. Changing them alters no geometry and — from v2 — triggers no model call.

**Geometry built deterministically:** floors, wall segments, real door and window openings with jambs and lintels. Scope is one complete floor with up to eight mostly straight-walled rooms. Complex curves, split levels and uncertain exterior structure enter an explicit correction or unsupported state; they are never replaced with invented rooms.

**Catalog.** Roughly 24 admitted CC0 assets — seating, beds, tables and chairs, wardrobe and cabinet modules, kitchen counters, sanitary fixtures, display and ceiling lights, curtains, simple plants — from Poly Haven, Kenney, Quaternius and KayKit. Procedural walls, openings and cabinet variants are separate architectural components. A small material library of paint, wood, tile, stone and fabric uses ordinary descriptive names.

Each asset records: stable ID and version, GLB or procedural generator, preview image, licence and source, content hash, measured dimensions, origin and pivot, mounting surface, clearance envelope, material slots, allowed variants, triangle count and texture budget. **Catalog thumbnails are rendered from the actual admitted model.** A generic asset carries no implied supplier, availability or price. Parametric cabinetry resizes within declared bounds; a fixed chair does not stretch arbitrarily to fit.

## Features in detail

### Studio chrome

```text
 VibeEstimate / Apartment     Saved · Option 2       Undo  Redo
 ----------------------------------------------------------------------
 Rooms          Overview  Inside  Plan     Starting layout / Option
 Whole home     +----------------------------------+  Living-room wall
 Living room    |                                  |  Material / Add
 Kitchen        |        EDITABLE HOME             |  Selected change
 Bedroom 1      |    click a room, wall or object  |  Source / Details
 Bedroom 2      |                                  |  Change details
 ...            +----------------------------------+  Apply / Discard
 Checks (1)     Whole home · Living · Kitchen · + Save view
                Changes (2)                       Properties
```

Roughly a 220px room navigator, a flexible canvas, and an optional 300px inspector that shows **one task at a time** — catalog, properties and discussion reuse that region rather than filling the screen simultaneously. On phones the canvas stays full width and one bottom sheet opens at a time, with a room selector replacing the navigator. Not miniaturised desktop panels.

### Editing

Direct selection, tap-to-place, drag handles, **and numeric entry for every operation**. A translucent placement preview shows position and collisions before anything is applied. Selecting a surface exposes Material and relevant additions; selecting an object exposes Move, Rotate, Size where supported, Replace and Remove.

Wall and opening edits are reachable only from the Plan view and create an explicit layout revision, so **moving a sofa can never alter architecture**.

### Comparison

Comparison always names its baseline — *Starting layout · v1*. The baseline renders as a translucent ghost in the same view while the option renders solid, at one matched camera. Changing the comparison baseline is always an explicit user action.

### Change cards

The data structure and the "open this revision at this camera" behaviour ship in v1 even though every v1 change is manual. A card carries the room, the affected objects, a factual change list, the exact saved revision and the camera. This is the atom the rest of the product is built from.

### Entities

Planned in v1: `Scene`, `SceneRevision`, `ChangeCard` (shell), catalog `Asset` and `Material`.

Planned in v2: `PlanAsset`, `PlanCandidate`, `EditProposal`, `SpatialJob`, `SharedSceneSnapshot`, `ClientOption`, `Annotation`, `AgentTrace`, `Brief`, and the [platform contracts](v2.md#platform-contracts).

### Endpoints

`POST /api/scenes`, `GET /api/scenes/:id`, `POST /api/scenes/:id/revisions` (validated manual edits with the optimistic `baseRevisionId` check), `GET /api/catalog`. All owner-scoped through the existing `assertOwner` in `backend/src/store.ts`.

### States handled honestly

| State | Visible response |
| --- | --- |
| Empty scene | Offer the sample home or a simple plan, and say what happens next. |
| Asset unavailable | A dimensioned placeholder labelled as unavailable; identity preserved; replacement offered. |
| Unsaved or offline | Keep the edits, show *Waiting to save*, reconcile revisions before reporting *Saved*. |
| Newer revision | Compare with latest, preserve the user's work, explain the conflict. |
| Graphics or context failure | Keep the plan and object list usable; offer to retry the 3D view. |
| Successful step | A concise saved milestone and the next useful action. No invented progress, streaks or urgency. |

### Explicit non-goals

No upload, no recognition, no model call anywhere in the studio, no scene sharing, no client options, no multi-floor, no export beyond what already exists.

## Accessibility and device reality

Not deferred. **Reduced motion, larger targets and keyboard-first are real settings**, not only OS media queries — see [controls](controls.md#the-homeowner).

- A semantic room and object list outside the canvas.
- Selection, move, rotate, material and size changes all work through labelled controls; keyboard **and** non-drag touch alternatives are both required.
- Plan and list editing stay fully usable when WebGL is unavailable.
- Escape exits captured camera input; Reset view is always reachable.
- `role="status"` for saved state; the screen reader receives saved-state and selection updates, not every camera frame.
- 44px minimum targets, visible focus.

**Quality mode** — auto / smooth / plan-only — ships here, with an honest downgrade notice when the device struggles rather than a frozen canvas.

`frontend/src/app/globals.css:357` disables CSS animation app-wide under `prefers-reduced-motion` with `!important`, so any 3D motion must be gated in JavaScript via `matchMedia`.

**Performance targets** (targets, not measurements): load the scene code only on studio entry; at most 5 MB first-view assets on desktop and 3 MB on mobile, with the full home loaded progressively within 15/10 MB; at most 250k/120k visible triangles, 150/80 draw calls, 1K/512–1K textures. One shadow-casting light, bounded pixel ratio, shared geometry and materials, rendering on demand. Verify disposal over repeated studio entry and exit.

Follow `.agents/skills/impeccable/SKILL.md`: run `context.mjs`, load `reference/new-work.md`, then `craft-floor.md` immediately before editing UI, and write a surface brief at `frontend/.impeccable/surfaces/` for the studio. The `room.module.css` per-surface pattern is the precedent — a `studio.module.css`, not new globals.

## Spike: ADK-JS

Before [v2](v2.md) depends on it, prove on the real package that `LlmAgent` runs, `MCPToolset` connects, and `SkillToolset` loads a SKILL.md folder.

`adk.dev` documents Node ≥ 24.13.0 and npm ≥ 11.8.0; this repository is Node 22.17.1 with `engines: >=22.17.0 <25`, and published `@google/adk@2.0.0` exposes no `engines` field. If it does not run on Node 22, the clean fallback is that the three *new* services in v2 ship on Node 24 in their own containers while the existing `api` stays on 22 — the split topology makes this cheap.

## What carries forward from the existing plan

[docs/spatial-home-studio-plan.md](../spatial-home-studio-plan.md) supplies the technical detail under the [current precedence rule](README.md#relationship-to-the-existing-plan). Its findings are distributed as follows.

**Landing in v1:** the visual change card as the signature interaction (shell); measurement states; integer millimetres canonical with metres at the renderer boundary; the asset admission record; optimistic revision checks with readable conflicts; wall changes requiring the plan view and an explicit layout revision; camera, cutaway and daylight as viewing preferences that trigger nothing; the rule that a floor plan does not establish existing furniture, finishes, ceiling form, services or structural adequacy — and that an inferred sofa must never render as evidenced existing; blob-before-manifest commit ordering; the performance gates as targets.

**Landing in [v3](v3.md#what-carries-forward):** multiple floors and stair links; optional free movement; generated presentation imagery; opt-in Present and Follow; quantity in thousandths of the declared unit and multi-line proposals; and broader evaluation beyond the first 12 plans.

Its threat → control → required test table applies to all three releases.
