# v1 — A home, a shared design decision, and a saved agreement

The September 6 product direction supersedes the manual-only studio, separate public PoC and sources-first homepage. V1 is one complete product: create a project, choose a measured home, describe the desired design, inspect real Gemini edits, discuss the same home with the designer, accept an exact version, and leave with a stored draft agreement.

Implementation and verification are in progress. Requirements below are not claims of completed checks. The standalone Pascal PoC remains in `../pascal-poc/`; application work continues on `feat/v1-home-journey` in a separate worktree. Executed results, model attempts, screenshots and recordings must be recorded separately.

## People and value

The **designer** creates a private home project and a named design assistant, starts a shared design room, invites the homeowner, reviews the homeowner's accepted option and prepares a draft agreement. The **homeowner** joins with a separate identity, sees the same home, discusses preferences, asks the assistant for changes and accepts a saved version. Both see the authoritative design and preserved conversation.

The **design assistant** uses the existing server-side Gemini connection to fill titles and briefs, select admitted furniture, lights and finishes, and explain actual edits. A bounded drafting task describes the accepted design in an agreement. Assistant activity corresponds to actual requests and persisted results; coding-agent collaboration is not presented as product-agent activity.

People give a brief or message, not empty forms. AI and canonical data supply editable names, descriptions, inventory, quantities and summaries. Do not invent agreed scope, client statements, confirmed dimensions, prices or signatures. Commercial terms remain unresolved until supplied and confirmed. Recorded design acceptance and designer review are not electronic signatures or a legally executed agreement.

| 5. | 6. Design to agreement | Homeowner accepts saved revision → designer accepts same revision → generate draft agreement → reopen room library → download | Persisted draft tied to exact revision, requests, inventory, assumptions, unresolved terms and both decisions. ## Scene, catalog and Gemini

Canonical versioned data is authoritative; the actual Pascal renderer is a mirror. Compile shared schema/core to JavaScript and declarations for production Node and Next.js, without a server renderer dependency. Store integer millimetres, explicit axes, bottom-centre pivots and clockwise Plan rotations. One floor has at most eight rectangular rooms, shared walls stored once and real openings. Template measurements and the assumed 2.8m ceiling remain disclosed; this is design visualization, not a surveyed construction plan.

The three authored floor plans are deterministic, distinct and validated. Show actual geometry thumbnails. Admit the local models needed for living, sleeping, kitchen, bathroom, work and lighting: GLB, measured bounds/pivot, material slots, hash, source/license and actual-model thumbnail. No arbitrary asset URLs, supplier or price claims. Production resolves admitted same-origin assets over HTTPS; loopback remains supported. Independent Plan survives graphics failure. Lighting is illustrative and does not calculate wall occlusion or engineering photometry.

The host supplies identity, project, base revision, request ID and semantic selection. Gemini cannot redefine them. A selection may be whole home, room, object, one surface or room region. A room includes only its facing surfaces; the opposite side of a shared wall is read-only context.

The model receives the scene, catalog/materials and collision-checked placement candidates. Additions choose supplied placement IDs; deterministic code supplies dimensions, mounting, coordinates and IDs. Existing-object movement, rotation, permitted resize, replace/remove, lights and finishes use strict operations. AI cannot change architecture. Validate the entire patch's syntax, assets, geometry, locks, collisions, door clearance and scope before publication. Failure preserves the previous scene. Derive factual change lists from applied operations; treat generated prose as untrusted text.

Use existing `@google/genai` and explicit authorized Vertex configuration, server-side only. A generation fills title/brief alongside its patch. Summary/agreement generation uses the exact saved scene and decisions on a user action. Viewing, orbiting, selecting, comparing and saving make no model calls.

Maximum eight operations and two reserved attempts per generation; one active spatial job per owner and persistent project/owner attempt ceilings. Fallback advances only on a definite recoverable upstream response to a separately configured verified model. Validation failure, timeout and ambiguous network outcome never silently redispatch. Persist attempt/phase/result, allow checking the original request, and prevent late publication after cancellation or changed revision. Work stays in a bounded live HTTP request or authenticated managed task; no detached Cloud Run background work.

## Persistence and shared decisions

Firebase verifies separate designer/client identities. Every API authorizes owner or exact room membership. Private homes do not become public through URLs. Sharing is explicit. Client scene permissions never grant private designer proposal authority.

Write immutable content before an atomic head update, with chunks at most128KiB. Keep the gateway's48KiB JSON limit. Every mutation carries request ID/base revision. Replay returns the original result; changed payload under the same ID is rejected. Preserve concurrent candidates and explain conflicts. Restore creates a new revision. Store actor and exact source request; messages retain the real sender. Shared editing scope is explicit and reconstructed server-side.

Homeowner acceptance stores the current revision, actor and timestamp. Designer approval requires that same accepted revision. A changed head makes old decisions ineligible for a new agreement while retaining the historical records. Each agreement stores its revision, decision records, source requests, generated body, model metadata and immutable version. Both members may reopen/download; unrelated users are denied. Download returns the stored version, not another model response. Unknown commercial terms remain visible in the **draft agreement**.

## Scope boundaries

The primary release starts with measured templates. Image upload remains a separately gated addition unless explicitly included: scale, original-image preservation, uncertainty overlay and measurement review cannot be replaced with a plausible invented home. Do not expose an unfinished upload control.

The designer-created assistant is a named/configured assistant attached to real shared design rooms. Website embedding, an independently deployed multi-service crew, multiple floors and external submission remain later scope. Existing proposals support confirmed commercial terms; a generated design must not masquerade as a previously agreed scope. Preserve original evidence, integer-money totals, included work, missing-price checks and exports.

## Threats and required tests

| Threat | Enforcing control and proof |
| --- | --- |
| Cross-user/room access | Verified UID plus authorization on every scene, job, revision, decision/export; unauthenticated/unrelated users denied and client projection tested. |
| Model scope/asset injection | Strict schema, admitted IDs and host scope; unknown fields/assets, opposite wall face and architecture rejected atomically. |
| Wrong geometry/rendering | Canonical checks plus actual Pascal bounds, opening ray tests, material slots, real lights and normal 3D screenshots. |
| Duplicate spend/late results | Reserved receipts and budgets; replay, exhaustion, ambiguous timeout, cancellation and stale publication tests. |
| Lost history | Immutable content plus atomic head; restart/reload, concurrent tabs, restore, storage failure and exact export checks. |
| Approval covers changed work | Role and exact-revision checks; stale or wrong-role acceptance cannot produce a new agreement. |
| Invented agreement | Exact saved inputs, unresolved terms and explicit human decisions; no fabricated prices, signatures or prior scope. |
| Leaked credentials/private records | Server-only config, bounded gateway, private authorization and public artifact/browser-log scans. |
