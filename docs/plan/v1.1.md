# v1.1 — Pascal proof of concept, then image-to-layout and precise editing

This is the current spatial delivery plan. It supersedes the earlier manual-studio-only sequence in [v1](v1.md), while preserving the existing application and its release work. These stages are planned acceptance gates; executed results belong in the relevant verification record.

## 1. Direction and delivery order

Build a **standalone Pascal PoC first**, prove its schemas, geometry, edits and browser rendering, and review it with the user before integrating anything into VibeEstimate.

Use both views of one shared scene:

- **2D Plan:** measurements, wall/opening corrections and precise region selection.
- **3D Overview and Inside:** proportions, furniture placement, materials and spatial experience.

We do not need to invent a programming language. Define a small, versioned **JSON scene and edit format**. Our parser validates that format; deterministic code builds or updates the scene. Later, an LLM produces the same format.

The specialised image agent comes after the PoC. It interprets floor-plan images into a proposed layout. It does not replace the syntax parser or establish accuracy merely by returning valid JSON.

Every stage ends with a working local website, screenshots, executed checks and a short review checklist. **Fix issues and incorporate the user's feedback before starting the next stage.**

## 2. Standalone Pascal PoC

### Setup and reusable boundaries

Create `../pascal-poc/` relative to the application repository root as an independent local Git repository with its own task branch, npm workspace, lockfile, dependencies, browser binaries, caches and test reports.

- Preview: `http://127.0.0.1:3110`.
- Match the application's Next.js 16.3.4 and React 19.2.8 baseline.
- Start with matched Pascal packages: core/viewer `0.9.2` and nodes `0.1.1`; verify against their published declarations.
- Use Pascal's architectural engine and viewer through an adapter. Its repository is MIT licensed; model and texture licences require separate admission records. See the [Pascal repository](https://github.com/pascalorg/editor) and [licence](https://github.com/pascalorg/editor/blob/main/LICENSE).
- Keep all PoC assets local. No Firebase, model calls, credentials, cloud services or imports from the existing application.

Organise the reusable code into:

| Module | Responsibility |
| --- | --- |
| `scene-schema` | Versioned Zod schemas, units, IDs, catalog references and configuration. |
| `scene-core` | Geometry validation, permitted edits, selection rules, atomic changes, revision history and conflicts. No renderer dependency. |
| `pascal-adapter` | Convert canonical scenes into Pascal nodes, translate selection events, expose actual rendered geometry for testing and dispose resources. |
| PoC website | Plan/3D views, selection controls, JSON examples, validation errors and local persistence. |

Pascal's internal state is a rendering mirror. Our scene document and revision repository remain authoritative. Disable or contain competing hydration, autosave and history behaviour.

### Scene syntax and edit contract

Use these interfaces:

- **`SceneDocument`:** one populated level, rooms, shared walls, openings, catalog instances, materials and measurement provenance.
- **`ScenePatch`:** permitted operations with explicit targets and parameters.
- **`SelectionScope`:** selected IDs, surface or region, locked entities and allowed operations.
- **`SceneRevision`:** immutable document reference, parent revision and change description.
- **`SceneRepository`:** load, save and compare-and-swap revision operations; implemented locally first and by the API later.

Store positions and dimensions in integer millimetres. Define axes, origins and rotations explicitly; convert to renderer units only inside the adapter.

A future LLM response can be as small as:

```json
{
  "schemaVersion": 1,
  "operations": [
    {
      "op": "setMaterial",
      "entityId": "wall-3",
      "surfaceId": "living-room-facing",
      "materialId": "paint-warm-white"
    }
  ]
}
```

The host supplies the base revision, request ID and selection scope separately. Model output cannot redefine them.

Support furniture placement, movement, rotation, replacement, removal, permitted resizing and surface-material changes. Put architectural changes in a separate explicit Plan-edit command group.

Reject unknown fields, operations, IDs, assets and materials; invalid dimensions, topology or openings; unsupported resizing; and edits outside the selection. Never execute generated code or resolve arbitrary asset URLs.

Validate the entire patch before publication. A failure preserves the last valid scene and explains the offending field or operation.

### Precise selection

Require selection before editing:

- Pick an object, wall face or room in Plan or 3D.
- Draw and adjust a rectangular region in Plan.
- Provide an equivalent semantic list and numeric controls for keyboard and touch.

Highlight the selection and list its affected entities. Rectangle selection includes fully contained objects; boundary-crossing objects remain visible as context unless explicitly selected.

Freeze selection when submitting a patch. Existing changes affect selected entities only. Region placements must fit inside the region; object movement must remain valid within its room. Wall additions must respect their mounting surface. Locked objects remain unchanged.

### Visual standard

Start with an accurately measured **5 × 4 m room**, 200 mm walls, a 900 mm door, an 1800 mm window and a disclosed 2.8 m ceiling. Add a second deterministic fixture containing two adjoining rooms to prove shared-wall handling.

Use real wall thickness, door/window holes, reveals, jambs and correctly scaled furniture. Admit six local furniture/decor assets with measured bounds, pivots, material slots and actual-model thumbnails.

Generate a labelled PNG floor plan from the first fixture for the later image-agent stage. Keep its ground truth in the test harness.

Maintain VibeEstimate's navy/red visual language, restrained controls and canvas-first layout. The JSON workbench belongs in the PoC developer panel.

## 3. PoC stages and review gates

| Stage | What the user can inspect | Required proof before review |
| --- | --- | --- |
| **P0 — Pascal boot and isolation** | A measured room in the browser, Plan/Overview/Inside controls and renderer status. | Reproducible install/build; actual Pascal 3D rendering; local assets; no application or cloud dependency. |
| **P1 — Schema to layout** | Load the single-room and adjoining-room examples; inspect dimensions, openings and furniture; download the fixture PNG. | Correct units, bounds, shared walls and real openings; invalid scenes retain the previous valid layout. |
| **P2 — Selected edits** | Select a wall, object or region; run example edit JSON; inspect affected entities and validation messages. | Correct geometry/material changes, unchanged neighbours, collision checks, selection enforcement and atomic rejection. |
| **P3 — State and configuration** | Save/reload, undo/redo, compare revisions, import/export fixture JSON and switch quality modes. | Deterministic replay, duplicate-request handling, preserved conflicts, storage failures and view settings that do not alter geometry. |
| **P4 — Acceptance rehearsal** | Complete the workflow on desktop/mobile and inspect the visual test report. | Full verification passes, normal 3D screenshots reviewed, graphics fallback works and the user accepts the PoC. |

Local persistence uses IndexedDB with immutable revisions and an atomic head update. Undo creates a new revision. Two tabs saving against the same base produce a readable conflict while preserving both versions.

Each stage produces a conventional commit after verification. Reports distinguish automated results from the user's visual acceptance.

**Integration starts only after P4 acceptance.** If Pascal fails a required capability, record the exact failing fixture and limitation. Do not silently substitute a renderer or count a 2D fallback as successful 3D rendering.

## 4. Integration and AI stages after PoC acceptance

Promote the proven modules into the application workspace while retaining `frontend/` and `backend/` responsibilities. Replace the local repository with owner-authorized API persistence.

Use an isolated integrated preview on frontend `3100`, API `8181`, Auth emulator `9299` and Firestore emulator `8285`. Preserve the existing connected development environment.

| Stage | Website experience and implementation |
| --- | --- |
| **I0 — Package integration** | Open the proven sample through VibeEstimate. Connect verified identity, ownership, saving and revisions without changing scene semantics. |
| **I1 — Specialised image agent** | Upload a floor-plan PNG/JPEG, inspect an extraction overlay, establish scale, correct uncertainties and accept the layout. |
| **I2 — Complete home and manual studio** | Explore an authored apartment and imported layouts in Plan/Overview/Inside. Place and edit furniture, change materials and explicitly edit architecture in Plan. |
| **I3 — Targeted AI edits** | Select a surface/object/region, describe a change and receive a validated furniture/material patch. Compare, undo or retain the resulting working option. |
| **I4 — Options and history** | Compare against a named baseline with matched cameras; reopen exact historical revisions and recover conflicting edits. |
| **I5 — Complete rehearsal** | Complete upload → checked layout → selected edit → saved option, including failures and the existing proposal workflow. |

### Image interpretation

Before I1, complete the official TypeScript ADK compatibility spike in an isolated worker runtime. Use Surveyor and Stylist as bounded roles in one spatial worker; broader multi-agent orchestration remains later work.

Surveyor returns a **`PlanCandidate`** containing proposed geometry, source-image coordinates, dimension labels and uncertainties.

- Accept PNG/JPEG up to 4 MiB and 20 megapixels.
- Preserve the private original and crop/rotation transforms.
- Overlay extracted geometry on the source.
- Require calibration or a known dimension when scale is missing.
- Distinguish plan-labelled, user-confirmed, calibrated, assumed and unknown measurements.
- Keep ceiling heights, furnishings and finishes absent from the drawing visibly unconfirmed.

Only the checked candidate becomes a scene. Begin with the generated room and its rotated, blurred and unscaled variants; broader accuracy claims require held-out plans.

### Application contracts and controls

Retain owner-scoped scene creation/read/revision and catalog endpoints. Add private plan upload/read, spatial job start/status/cancel, candidate acceptance and selected-edit requests.

Binary uploads use a separately bounded route. Keep the existing 48 KiB JSON gateway limit. Store immutable scene chunks of at most 128 KiB, write content before the head transaction and preserve request deduplication and conflicts.

For AI edits, the server reconstructs permitted scope from the selected revision. Neighbouring geometry is read-only collision context. Architectural edits remain manual.

Bound work to one active spatial job per owner, one extraction plus one explicit retry per source revision, two model rounds, four tool reads per round and eight operations per patch. Reserve each model attempt before dispatch. Cancellation and stale revisions prevent late publication; ambiguous outcomes never silently trigger another paid call.

Viewing, selecting, orbiting and saving make no model calls.

Expand the catalog to approximately 24 admitted assets and the sample to one floor with up to eight mostly straight-walled rooms. Keep new spatial sharing/exports, multiple floors and the wider agent crew in later releases.

## 5. Verification and remaining v1 work

### Autonomous verification

Test the scene at three independent levels:

1. **Canonical data:** expected dimensions, transforms, selections, revisions and validation results.
2. **Actual renderer geometry:** inspect Pascal/Three mesh bounds and transforms, ray-test real openings and verify material assignment.
3. **Browser experience:** real pointer/keyboard interactions and fixed-camera screenshots after rendering settles.

A passing JSON assertion alone does not prove correct rendering.

Required scenarios include:

- Millimetre round-trips, shared walls, opening placement, furniture bounds and supported resizing.
- Selected-wall material changes that leave the opposite face and neighbouring walls unchanged.
- Valid placements, collisions, locked objects, forbidden scope expansion and rejected atomic batches.
- Save/reload, undo/redo, duplicate requests, concurrent tabs, corrupted imports and failed storage.
- Missing assets, graphics initialization/context failure and a usable independent 2D Plan fallback.
- Every public schema/configuration variant, invalid configuration handling and view-only preferences.
- Playwright at 1440, 390 and 320 pixels; keyboard, non-drag touch, reduced motion and accessibility checks.
- Typecheck, lint, production build, unit tests and browser tests through one local verification command.
- First-view asset budgets of 5 MB desktop/3 MB mobile, rendering measurements and resource disposal across repeated entry/exit.

PoC browser tests reject external network requests. Screenshots must include the normal 3D renderer; fallback screenshots are separate evidence. Software-rendered browser tests establish correctness, not physical-device frame rates.

After integration, add authentication and cross-user denial, upload/model failure, job cancellation, budget exhaustion, persistence and existing proposal/money/revision regressions. Keep deterministic fixtures and bounded live-model results separately labelled.
